# Applying the method to a 6809 game (Williams WPC)

The agents are written for Stern SAM (ARM). The same method works on the older 6809 boards: Williams WPC
(1990-1999) and, with other addresses, Data East / Sega / Stern Whitestar. This page lists what changes. It
was measured on Terminator 2 L-8 (WPC, first DMD generation, 1991); facts are tagged observed / code /
inferred. Agent A's sections still apply in the same order (section 13); only the tools and the hunt for the
OS differ.

## 1. Identify and map

| Item | WPC (T2 L-8 as the example) |
|---|---|
| Set | SHA1 of each ROM against PinMAME `src/wpc/sims/wpc/full/<game>.c` and `src/wpc/wpcgames.c` (code). A zip of "sound ROMs" is often a different revision (T2: prototype P-1 sound, PinMAME `t2_l2sp1`). |
| Game ROM | One file, 512 KB on T2. Banked: 0x4000-0x7fff is a 16 KB window, bank register `0x3ffc`; bank B maps to file offset `(B - 0x20) * 0x4000` for a 512 KB image (code). The last 32 KB is fixed at 0x8000-0xffff. Byte 0 of each bank holds the bank number (boot check, code). |
| RAM, IO | RAM 0x0000-0x2fff (+0x3c00-0x3faf), DMD page windows 0x3800-0x3bff, ASIC 0x3fb0-0x3fff (sound data `0x3fdc`, DMD visible page `0x3fbf`, bit shifter `0x3ff4`/`0x3ff6`) (code). |
| Sound | Pre-DCS boards (1990-93) are a second 6809 with YM2151, DAC and CVSD, ROMs U14/U15/U18; a call is one byte, or `0x7a` + byte for the second page (observed). DCS games (1993 on) are different. |

## 2. Tools

| Tool | Status on 6809 |
|---|---|
| PinMAME as a library + per-instruction hook | Works: [../tools/rom/emulator_trace/pinmame_m6809_hook.patch](../tools/rom/emulator_trace/pinmame_m6809_hook.patch) adds a hook before every 6809 instruction (cpu number, PC; registers readable and writable), memory read/write, ROM bank, and a WPC write hook that can drop a write (to mute game sound while the script drives the sound board). Build `pinmame_shared` with CMake (`make` target `pinmame_shared`, not `pinmame`). |
| Ghidra | Works with processor `6809:BE:16:default`: load the fixed 32 KB at 0x8000, one overlay per non-empty bank at 0x4000. You must teach it the far-call and inline-argument conventions (section 3) in a pre-script, otherwise most functions decompile as garbage. **Mark the inline bytes of every call site as data first, then disassemble the sites** (three passes: find, mark, disassemble with the fall-through moved past the data). A one-pass loop that disassembles each site as it goes flows into the next sites and decodes their arguments as opcodes before they are marked, and `createData` then fails silently: on T2 most sites after the first in a handler were lost (209 functions with bad instruction data; three passes: 7). Also put each site's argument bytes in a PRE comment (`setPreComment`, with `DecompileOptions.setPRECommentIncluded(true)`) so the C keeps them, and create functions at the task entry points the task-create wrappers carry inline (id, fn, bank), which nothing calls directly. T2: 1,685 functions; the 184 that fail are mostly the wrappers themselves. |
| capstone | `CS_ARCH_M680X` + `CS_MODE_M680X_6809` for quick static disassembly. |
| Pinball Asset Decryptor | **Not usable for early WPC graphics** (observed on T2: it finds the tables but writes noise for most pictures, no fonts) and has no pre-DCS sound. Capture media from the emulator instead. |

## 3. Finding the OS (the conventions that break a naive disassembly)

| Convention | How to find it | T2 example |
|---|---|---|
| **Far call** `JSR far_call ; .dw addr ; .db bank` | The most-called fixed-area target whose callers are followed by 3 data bytes | `0x88f5` (code) |
| **Inline-argument wrappers**: `JSR wrapper ; .db args...`, the wrapper pulls the return address, reads N bytes, advances it | Measure N in the emulator: record the stack pointer at each JSR into the fixed area, see where execution resumes in the caller; confirm with a static scan of the wrapper (`ldx n,s ; ld? ,x+ ; stx n,s`). Without this, Ghidra and capstone decode the arguments as opcodes. | 91 wrappers, 1 to 5 bytes (code + observed) |
| Task scheduler | The `task_sleep` wrapper (1 inline byte = ticks) is the most-called; tasks save S on switch, so stack-based measurements across it give false lengths: force its length by hand | `0x8346` (code) |
| **Registry of far pointers** at the start of the fixed area | 3-byte entries (addr, bank) from 0x8001: first game hook vectors (called through one dispatcher with a 2-byte inline pointer), then every data table. **Check alignment**: one 2-byte constant shifts every later entry; take the true entry addresses from the code's `ldx #imm` immediates. | 0x8001-0x828e; 2-byte word at `0x81ae` (code) |
| Table format | `u16 count, u8 record size, records`, read by one generic indexer (X = registry entry, A = index) | `0xac5b` (code) |
| Name and per-switch tables start with an **unused entry 0** ("NULL", "INVALID SW. NUMBER") | Index = position + 1. Confirm the switch handler mapping by watching the handler addresses while hitting switches | T2 switch handlers 3d:4931 (observed for 10 switches) |
| **Carry polarity of the test routines** | Read it from the code before writing a rule: the bit test ends `anda mask ; suba #1`, so **carry clear = bit set** (`bcs` after a lamp test = lamp off); `task_find` returns carry clear when the task runs. Check on a known case (an outlane that pays a lit special). A lamp scan built on the test (`first lamp from A whose test gives carry clear`) then returns the first **lit** lamp | T2 `0x9edd` / `0x9fa0`, `0x8690` (code); an escape route rule was first written inverted |
| Wrappers an `ldx n,s` scan misses | Wrappers that read the return address at offset 0 (`ldx ,s ; ldd ,x++ ; stx ,s`), through `ldu n,s` after a `pshs`, or that never return (**far jump**: `.dw addr ; .db bank`, then `jmp [ptr]`): list every fixed-area JSR target whose caller is followed by non-code bytes, and mark the far jumps as terminators (no fall-through) | T2 `0x8679` (2), `0x8948` / `0x8983` far task create (3), `0x892f` far jump (3), `0xd730` glyph draw (font, x, y: 3) (code) |
| Lamp and flag bit ops: `A` = bit, `B` = buffer offset (lamps, flashing lamps, game flags) | **The lamp bit index is 1-based** (1 = lamp 11, 0x40 = lamp 88): check by calling the set-bit routine with known values and reading PinMAME's lamp output. A 0-based guess shifts every lamp by one and still looks plausible | T2 `0x9e7f` set, `0x9e92` clear, `0x9edd` test (observed) |

From the registry, each table is named by who reads it and by count matches with the name tables (the
adjustment and audit name tables have the same count as their definition tables): score values (4-byte BCD),
display effects and lamp effects (priority, flags, function far pointer), sound calls (call → board byte),
standard and feature adjustments (default, min, max, step or choice list, render function), audits, and
EN/DE/FR text tables for switches, lamps, coils, flashers, adjustments and audits (T2: 71 tables).

## 4. Emulator set-up gotchas (WPC)

| Problem | Fix |
|---|---|
| A fresh NVRAM stops on "FACTORY SETTINGS RESTORED" / "BOOKKEEPING TOTALS CLEARED" | Boot once, save the `.nv`, start every run from that copy (observed). |
| The coin door switch set through `PinmameSetSwitch` is overwritten | Turn libpinmame keyboard handling on and toggle the door with the END key (keycode 78) at boot (observed). |
| Start is ignored | Hold the start key about 0.8 s; with default pricing, 2 coins = 1 credit (observed on T2). |
| Multi-player game desyncs on ball 1 | A simulated autoplunge fired during the second start press; turn autoplunge off until every start press is done, then plunge (observed on T2). |
| Scripted switch hits are lost now and then (T2: about 1 in 6 jet hits, several top lane hits; same loss on every rerun of a script, so it looks like a rule) | With keyboard handling on, PinMAME's ball simulator (`sim.c`, `sim_run`) resets every playfield switch that has a simulator key on each VBLANK, so a hit survives only if the CPU scanned it before the next frame. Press the "Switch/Simulator" toggle (DEL, `PINMAME_KEYCODE_DELETE`) once at boot: every hit then registers (observed on T2: 7 of 7 in a test that lost 3). Rerun every rules trace made before the fix (code + observed). |
| A switch hit is still ignored after the DEL fix, but only some of the time (T2 plumb bob: the 2nd of 5 tilt hits, then a different one when the gap changed) | The scripted closure is too short for that switch: with 40 ms pulses the handler was sometimes never called; with 150 ms every closure counted. Before calling an ignored hit a rule, rerun with a longer pulse and watch the handler's entry (`T2_WATCH`). The real rule was a 14-tick debounce task (about 0.23 s, one tick = 16.35 ms measured from a `task_sleep`), not a settling time (observed + code). |
| Mechs (T2's gun) | `PinmameSetHandleMechanics(0xff)` uses the driver's simulation (`mech_addLong` in the game's `.c`) (code). |

## 5. Forcing effects and sounds (call injection on 6809)

The scheduler's idle loop runs on the system stack between tasks. In the hook, when PC reaches it and an
injection is pending: push the idle loop's address on S, set A (or D, X) to the argument and PC to the
target. The target returns to the idle loop. Note the hook for the target's first instruction is skipped,
so log the injection yourself. On T2 (idle loop `0x9767`) this started every display effect (deff_start
`0xc791`), lamp effect (leff_start `0xcc3a`) and sound call (`0xbdfb`) on demand; 140 of 189 sound calls
sent their byte in attract mode (observed).

Two traps (observed on T2): **confirm which table is display and which is lamps by capturing**, not from the
record layout (the first guess was swapped: the 11-byte records with a function pointer are lamp effects that
can also start a deff); and **inject in a game, not in attract**: the attract show keeps drawing over the
forced effect, and most effects carry a flag that rejects them outside a game (T2: flag `0x08` allowed in
attract, checked against RAM `0x87`). Start a game, leave the ball in play, then inject. A third one cost a rerun: keep every injected
argument in **one base** from the scenario to the parser (a decimal id read as hex mislabels every id from 10 up,
silently). Capture DMD frames on every change (PinMAME raw mode gives
4 shades, 0-3, on early WPC) and cut them by injection time; capture each sound command to WAV by writing it to
`0x3fdc` from CPU context, waiting for 1 s of silence, then sending `0x00`.

**Effects that a forced start cannot show** (they read game state; T2 had 12 of 74 after forcing in a game).
List each one's `deff_start` call sites from a static scan, read the code around the site, and reach that state
in a scenario. Two cheap ways worked on T2 (observed): **high score entry** (grand champion banner, initials
entry): poke player 1's BCD score to a huge value just before the last drain, then press the flipper switches;
and **attract or service-only effects** (`PRESS "ENTER" FOR TEST REPORT`, `PINBALL MISSING / PLEASE WAIT`):
force them in attract and keep only the first frames, before the attract show draws over them. Effects that show
a running mode's value (hurry up) need the mode itself, and a randomly chosen award may need many balls.

## 6. Rules: start from the feature audits

The fastest map from a feature to its code is the **feature audit table**: every award increments its audit
through one OS call with inline arguments (T2: `JSR 0x88d5 ; .db 00,N`). A byte scan for that call gives, for
each audit name (SKILL SHOTS, GUN HITS, MULTIBALLS, SUPER JACKPOTS, ESCAPE ROUTES...), the address of the
award code; 35 of 38 T2 feature audits have one direct site (code). Read the code around the site, then write
a scenario that reaches it, with a PC watch on the site and its branches (filter the watch by bank: the same
address runs in other banks).

Three traps seen on T2 (observed):
- **Switch "seen" counters.** The OS keeps a per-switch counter (T2: RAM 0x174e + switch index) that marks a
  switch as working. Some rules read it: T2's gun assumes a hit when all five targets are broken, and otherwise
  waits about 0.9 s for a real target switch. A scenario that does not close the right switch in that window
  reads as "the rule never fires".
- **First hit of a ball goes elsewhere.** The skill shot takes the first target hit of each ball, so a rule
  test on the same targets must spend that hit first.
- **"Ball save" vs "no valid playfield".** Both return a drained ball. Test with and without a scoring switch
  after the plunge: T2 saves any drain before the first scoring switch, and every drain within about 8 s of the
  plunge after it.

## 7. Adjustment choice labels without the service menu

Choice-list adjustments point to a list of 16-bit text ids, one per value. On T2 (code): `0x8000 | i` is
system message `i` (table of u16 pointers at 3c:4004, count at 3c:4001), a plain `i` is game text `i` (the
EN game text table from the registry, 30:4bee), and `0xc000 | i` is a third table (serial-port settings,
not needed). Decoding the lists statically gave 38 of 41 lists in full, faster and more reliable than
crawling the menu in the emulator, where quick key presses were lost (observed).

## 8. DMD fonts (early WPC)

Find the text routine first: the one that walks a format string and switches font on a letter (T2:
`display_text` 0xd60c, `ldb ,y; subb #'A'`, then a 3-byte (address, bank) entry from a table whose address
is a word in the fixed bank's registry, T2 0x8285 → 0xe28b). A font record on T2 (code, 25 fonts checked by
rendering): char ranges as (first, last) pairs ending with 00, height, max bytes per row, then one 2-byte
glyph pointer per defined char, same bank; a glyph is its width then `height` rows of ceil(width/8) bytes,
least significant bit leftmost. Records with height 0 are picture sets in another format. Render every font
to PNG and look at it before trusting the decode; a wrong offset shows at once as shifted characters.

**Text layout per effect for free:** log the text routine's entry in the emulator (T2: X = font record,
Y = the rendered text in RAM, RAM 0x0533/0x0534 = x, y anchor) while forcing each display effect: one row
per draw gives font, position and text (T2: 197 draws in 50 effects). Label rows by the injected id, not by
the scenario's mark, and cut each effect at its first return to the score display, since queued or attract
effects can draw in the same window.

## 9. Lamp groups, BCD accumulator, switch fallbacks (read from the ROM, WPC OS of the T2 era)

Found while deriving T2's ramps, Payback, video mode and side features from the code (rules text: the game repository).

- **Lamp groups are ROM data, not something to observe.** A registry word (T2: 0x81c2) points to a table of 2-byte pointers to group
  records: link word, `0xfa`, ops, `0xfa`. Ops are stored forward **and mirrored** so the engine can also walk the group backwards:
  `0x85 a b 0x85` = lamp bits a..b, `0x81 g 0x81` = include group g, plain bytes = single bits. Lamp bit n is lamp n-1 in column/row order (bit 1 = lamp 11).
  The engine is one interpreter (T2 `fix:ae96`) with a callback per call: set-next-unlit (reverse walk = ladders that fill from the top), test-all-lit
  (**carry clear = all lit**), clear group, blink group. Read the group by decoding that table before trusting any group list made from lamp traces.
- **Carry polarity:** the OS bit tests return **carry clear when the bit is set**; `task_find` carry clear = found; a "test group" call returns carry clear when every lamp is lit.
  Reading these backwards is the commonest mistake when porting a rule.
- **5-byte BCD score accumulator:** one helper loads RAM 0x0577 from a 5-byte value, another clears 0x057c, one adds 0x0577 to 0x057c with `daa`, one stores 0x057c back.
  A constant is a ten's complement (T2 hurry up: 99 99 92 30 60 = -76,940), so "value falls by n per step" is an add. Ten digits, byte 1 holds the millions.
- **Per-player counters** are arrays of 4 bytes addressed through one helper (T2 `fix:fb29`: X += player - 1); a counter address in a listing is the base of that array.
- **Broken-switch fallback:** many scoring handlers end with "if switch X's seen-counter (RAM 0x174e + entry) is 0, run switch X's handler yourself through a task create
  from the switch table" (T2 `3d:5eab`, entry = switch position + 1). It does nothing on a working machine; do not port it as game logic.
- **A display effect can be the whole game:** T2's video mode is deff 0x20 (a task in bank 2b with its own spawner, sight and enemy tasks), started by the lamp effect table's last
  field (a deff id). When a mode has no obvious game task, look for a deff or leff that starts it.
- **Feature timers in "task a4" style tasks** count in `task_sleep` units (T2: 16 x 4 ticks per second) and share one pause helper (no ball in play, effects running);
  find that helper first, it explains why timers stop in attract and in multiball.
- **A coil that no handler fires is fired by the game's fast switch hook.** WPC games register hooks for the IRQ (T2: init `810f`, closure test `8112`, coil-off `8115`
  in the fixed-ROM hook table, called by the OS interrupt) that watch the debounced switch columns and drive jets, slings and a kickback directly (T2 `fix:ecca`: switch bit,
  lit flag, retry counter, coil on in 1 ms, a pass counter for the pulse length, a longer counter for the re-arm). When the lane handler scores but never touches the
  coil, look in those hooks (`game_hooks.csv`), not in the OS dispatcher; a RAM-write watch on the driver shadow byte (T2 0x76 -> 0x3fe1) finds the writer in one run.
- **Output queue tables:** `8385 n` (coil) and `8392 n` (flasher) index a 2-byte-record table (coil or flasher code, on-time in 1 ms-ish ticks), then a 5-byte driver table
  (shadow byte, register, mask). The argument is not the coil number; read both tables. On-times of 0x40 / 0x20 match the ~64 / ~32 ms seen on the board.
- **`timer_test N M` is an equality test** on adjustment N (carry clear and Z = equal), not a threshold; reading it as "passes" gives the wrong branch.

## 10. Sound cue tables and the task tick (learned on Whitestar: Lord of the Rings)

- **Decode a cue table from its player routine, never from the data's look.** On LOTR (60:4198) a cue is a 7-byte
  header (priority, flags, channel, **n alternatives at +3**, chain chance, next cue) then n record pointers. Reading
  n from +1 (which often equals +3) made the next cue's header look like a record ("FD 02, length 9236"), and that
  fake record was taken for a speech/music duck for days. Check: every decoded record pointer must land inside the
  record table, and a "record" seen in many cues with the same odd length is suspect.
- **Alternatives vs sequence**: the player picks ONE record (random, or by the free channel) and queues a chained cue
  after it. Listing the records of a cue as one sequence makes the recreation play every variant at once.
- **Speech = one channel**: the cue's channel byte tells speech from effects (LOTR: channel 2), which is simpler and
  safer than guessing from lengths or commands.
- **Indirect plays**: scan for the player's far call with X loaded from a table (`ldx #table; lsl; ldx a,x`) and
  for record accessors (`ldx 14,x`); an inline-argument scan (`jsr play; .dw cue`) misses them (LOTR: 21 sites, 152
  table entries: countdowns, jackpot multipliers, member names).
- **Task tick is not fixed**: the scheduler pass waits for an IRQ-driven counter and then clears it, so a slow pass
  loses counts. Nominal 16.4 ms (16 IRQs at 976 Hz) measured 19-22 ms in play. Give the recreation the observed
  rate; the sound channels' busy times use a separate real-time counter (10 IRQs = 10.25 ms per unit).
- **Whitestar coil numbers are not PinMAME's.** The game's internal coil n drives ports 0x2000-0x2003 in order, but
  PinMAME's se.c maps 0x2000 to sol 9-16 and 0x2001 to sol 1-8: PinMAME index = n XOR 8 for n < 16 (LOTR, code +
  observed). A trace that shows "sol 9-11" where the code fires coils 0-2 is this, not a decoding error. Check on a
  coil with a known pulse (bumpers) and on the flasher list.
- **Motors that stop on a switch** (LOTR Balrog): the run loop re-arms the coil each tick while the start-position
  switch is still active, then adds a fixed overrun; it does not wait for the end switch. An emulator that never moves
  the switches shows one short pulse per run; a simulation must toggle the switches itself.

Last updated 2026-11-23 (section 9 sound cues and tick, Whitestar LOTR; first WPC game: Terminator 2 L-8; sections 6-7 rules and settings; section 5 state-dependent effects; section 4 lost switch hits and short pulses; section 8 fonts).

## 10. Full-walk code audit (learned on Whitestar: Lord of the Rings)

Owner rule: every rule, display byte, lamp and coil comes from the code, nothing from an emulator capture. The
method that delivers it in one pass (LOTR: `tools/audit/` in the game repo, `docs/rules/audit.md`):
- Walk the disassembly from every root: the switch handler table, the flipper tasks (the flipper dispatcher
  starts tasks, it is not in the switch table), every effect script, every far-call / task-start / jsr target,
  the vectors. Follow branches; record only *nodes*, the OS calls with a visible effect (coil, lamp, flag, leff,
  effect, display queue, cue, music, task, timer, audit, score), with the registers loaded before each call.
- Know the inline calls first (the OS routines that read their arguments from the bytes after the jsr): the
  walker must skip those bytes or it decodes data as code. List them before walking.
- Closures per switch and per task (calls, far calls and task starts followed) answer "what does this switch
  cause"; a per-effect table of the stores into the display packet buffer answers "which bytes reach the DMD".
- A second pass over clean code blocks with no static caller catches jump-table targets; flag them as "caller
  open", since some may be data. Coverage per bank (lines walked / listing lines) shows what is left.
- Plain RAM writes are not nodes: rule state (lane rotations, counters) still needs reading the routine. On
  LOTR the flipper tasks rotate a lane nibble in RAM and redraw the inserts from it, a feature the MPF build
  had missed until this audit.
- Closing every indexed RAM access (LOTR, 1,141 open after evaluating pointers, tables and caller arguments):
  1. Compute **live** routines from real entry points only (switch table, flipper tasks, CPU vectors, task
     block, effect and leff tables, dispatch tables, OS calls with inline arguments, tasks created by hand with
     `ld #code; st <task slot resume field>`). Do not count every `jsr` target of the listing as reached: calls
     from dead code or from data decoded as code inflate the "reached" set. Ignore argument values that only
     reach an access through call sites no live routine executes.
  2. For each jump table, read the field the code jumps through (`jsr [3,x]`), not every word of the record:
     on LOTR the eject table had a switch list at +1 and the handler at +3.
  3. An OS routine with inline arguments can have several entry points sharing them (LOTR menu dispatcher at
     692A / 693C / 695A); give the walker all of them, or the arguments are decoded as code.
  4. Copy the register state at each branch: a shared dict lets later instructions corrupt the values at
     branch targets.
  5. Read the remainder by hand into a table (routine, sites, ROM or RAM or stack, targets, proof address).
     Targets are whole structures from the ROM tables the code indexes (bit layers, task slots, menu records,
     NVRAM default descriptors, sound channels, score descriptors). Write ROM and stack reads to their own table,
     so "unresolved" ends up holding only dead code and data decoded as code, each with its evidence.
  6. Then close the sets per call site: a structure indexed by a register (lamp / flag layers, score descriptors,
     settings) gives a set of possible targets until each caller's index is traced. Record A, B, X, Y (and any
     index register added with `leax d,x` / `abx`) at every call, then follow the index to its source: an
     immediate; the caller's entry register through its callers; a RAM variable through each live writer; a ROM
     table with the index range read from the code; or a value a routine keeps. A 6809 routine keeps A when its
     first instruction is `pshs a` (pulled at return), or when neither it nor its callees write A outside a
     `pshs a` / `puls a` pair: check this on the code instead of clearing A after every `jsr`, or most `lda #n;
     jsr test; jsr api` idioms lose their argument. Mark a linear walk's loop pointers as first-pass only and read
     those tables by hand (Lord of the Rings: the music priority table had no record of the type a flag-test
     branch needs, so that branch never runs). Operator-chosen indexes (menus, lamp tests) are a range, with the
     code that bounds it.

## 11. Service menu from the code (learned on Whitestar: Lord of the Rings)

1. Find the menu selector: a routine called with inline arguments (Lord of the Rings 57:695A: variable word,
   max byte, redraw word, then max+1 handler words), polled once per tick, that turns the buttons into a key code
   and jumps to `table[var]`. Scan the whole bank for `jsr selector` and decode every call: that list is the
   complete menu tree, with no gaps (LOTR: 43 menus, 276 items).
2. The level and item numbers go to the display as one packet (LOTR opcode 0xAA, level, item); the display ROM
   holds the item texts as string lists. Pair each CPU menu with its list by size and by the back links ("GO TO
   MAIN MENU"), and keep the display text even when it disagrees with where the code goes (LOTR: a line reads
   FILM STAR RESET but opens the installs menu; "GO TO MAIN MENU" in the printer menu returns to the audits menu).
3. Sub-screens are icon rows on the same selector: label each icon from what its handler does.
4. For each value screen, read the packet buffer byte by byte (count, opcode, parameters) and the record format
   dispatch: the edit routine and the display layout both branch on the record's format byte.
5. Write a generator that re-reads the tables from the ROM and fails when an address moves, and render the tree
   as a picture (Mermaid to SVG) for the owner to check.

## 12. Sound board status line (SST0) from the AT91 firmware (learned on Whitestar: Lord of the Rings)

Late Whitestar / early SAM-era sound boards (generation 3, AT91 ARM: `bios.u8` + script ROM `*-u7.*`) report one status
bit back to the CPU (Whitestar: SST0, bit 1 of the DMD/sound status port; PinMAME `desound.c` maps it to PIO P4). When the
game code waits on that bit, read the sound firmware, not a capture:
- The firmware at `bios.u8` 0x8000+ runs from RAM at file offset - 0x8000. Find PIO accesses by the pattern
  `mvn rX,#0xff00; eor rX,#k` (0xFFFF00FF ^ k: 0xCB CODR, 0xCF SODR, 0xEF OER, 0xFF PER) and list every SODR/CODR site.
- On LOTR the only P4 writer is a **script opcode** (0x1E, handler 0x93B8, operand non-zero -> set, zero -> clear): SST0
  is a beat / end marker that specific music and jingle scripts emit, not a command acknowledgement. Ask "which scripts
  contain the opcode", by walking every command's scripts (directory `u7[0x2C + 0x600*bank + 6*byte]`, compact table:
  k-th set mask bit uses word k), following goto / call / loop.
- Get the opcode operand sizes from the handlers (each byte read through the 1- or 2-byte operand readers); one wrong
  size (LOTR opcode 0x1F is 10 bytes, not 6) turns most walks into garbage. Opcodes 00 / 01 change size with a format
  word chosen at boot, so check which format the firmware settles on.
- Time a script in ticks: the script clock adds the tempo byte (opcode 0x0E) to an accumulator every 49 samples and ticks
  on carry, so ms = 255 / (sample_rate / 49 x tempo) x 1000; the sample rate is external (PinMAME), label it so.
LOTR worked example: `tools/sound/sst0_scripts.py` and `docs/sound_hardware.md` in the game's private repository (bonus
music FD 04 toggles SST0 every 144 ticks = 0.88 s, which paces the bonus screens).

## 13. Decompiling a banked 6809 DMD controller completely (learned on Whitestar: Lord of the Rings)
The Whitestar DMD board (6809, 32 x 16 KB banks in a 0x4000 window, fixed 0x8000-0xFFFF) can be decompiled with no capture:
- **Walk to a fixed point**, not from coverage seeds. Seeds: the vectors, the *first task* (reset stores its entry in a
  task stack frame, so no call reaches it: LOTR 0x8D6D), every entry handed to the task creator (`ldx #entry; jsr new_task`)
  and every hook stored for later (`ldx #hook; stx hook_var`), harvested from walked code and re-walked until nothing is new.
  Track the bank: after `lda #n; jsr select_bank` the window means bank n; packet handlers in the window run in the bank
  the dispatcher selects first.
- **List every indirect jump and explain each** (jump table cited by its use site; task/display hooks; coroutines
  `puls x; jsr ,x` = code after the caller's jsr; blitter `jmp ,u` into unrolled shift chains = base + 2*(x & 7)).
  A green walk = 0 unexplained sites.
- **Animations are scripts for an interpreter**: read each opcode's operand size from its handler, then walk all scripts
  with the script stack carried along (loop count 0xFF = forever, no fall-through; call/return share the 6809 stack);
  a native-call opcode whose routine never returns ends the path. The native routines found this way are new walk seeds.
- **Image format from the draw code**: directory of (bank, pointer) records indexed by id*3; a type byte selects raw or
  run-length streams written column by column; glyphs are ordinary images; text objects use string ids, some of them RAM
  buffers filled by the CPU's text packets (so the game's texts live in the CPU ROM, not the DMD ROM).
- Ghidra cannot follow flow into an overlay bank from fixed code (decompile fails); the bank-tracking walk listing is
  the fallback, say so in the inventory.
Tools to copy: LOTR `tools/dmd/dmd_walk.py` (`full_walk`), `dmd_objects.py`, `dmd_images.py`.

## 14. Rendering sound commands from a decompiled sound firmware (learned on Whitestar: Lord of the Rings)
When the game needs audio files and the rule forbids emulator captures, run the sound board's own logic in Python:
command directory, script interpreter with every opcode, the tick clocks, the voices and the mixer, each step citing
its firmware routine. LOTR (AT91 board, `tools/sound/sound_render.py` in the game repo) renders 629 commands this way.
- Render at the loudest volume level the game itself sends (find the clamp in the main CPU code), not at the board's
  reset gain: the MPF game can only attenuate.
- Read the sample address exactly as the voice routine does, per coding. On the AT91 board PCM reads data + 2 x index
  but IMA ADPCM reads data + index (index counted in nibbles), so the two codings step through the interleaved voice
  ROMs differently. Getting this wrong still gives a plausible-sounding signal (an IMA decoder turns any bytes into a
  random walk), so test intrinsic checks are weak: compare against a reference.
- A capture may serve as a confirm-only check (spectrum and 20 ms envelope correlation per command). PinMAME sweep WAVs
  of this board are sample-for-sample at the board rate (24242 Hz) though labelled 24000 Hz: compare in samples, or the
  1% drift kills the envelope match after a few seconds.
